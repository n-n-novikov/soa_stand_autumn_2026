# Orders — задание 1

Python, FastAPI, httpx и psycopg. Весь код сервиса находится в `app.py`.
База — PostgreSQL из стенда, таблица создаётся при запуске.

## Как проходит заказ

1. `POST /orders` проверяет тело, считает сумму `Σ qty × price_cents`,
   сохраняет заказ и отвечает `201 {"id": "…", "status": "pending"}`.
   В этом запросе нет обращений к Inventory или Payment.
2. Четыре задачи `asyncio` выбирают ожидающие заказы из PostgreSQL.
   Пока одна задача ждёт сеть, другие могут обрабатывать другие заказы.
   Блокировка выбора и набор занятых заказов не дают двум задачам взять
   один заказ. Это рассчитано на одну копию сервиса, как требует стенд.
3. Обработчик резервирует товар и оплачивает заказ. После подтверждения
   оплаты сохраняет `paid`. После `402` снимает резерв и сохраняет `rejected`.
4. `GET /orders/{id}` возвращает текущий статус и сумму, для неизвестного
   заказа — `404`. Ошибочное тело `POST` получает `400`.

В таблице отдельно хранятся публичный статус и текущий шаг:
`reserve`, `charge` или `release`. Например, после отказа банка мы сохраняем
`release`: повторная попытка будет снимать резерв, а не снова запрашивать оплату.
Публичный статус остаётся `pending`, пока резерв не снят.

## Что происходит при сбоях

- Каждый запрос оплаты использует `Idempotency-Key`, равный `id` заказа.
  Идентификатор, сумма и валюта при повторах одинаковы. По контракту Payment
  повтор не создаёт нового списания.
- Сетевой вызов ограничен тайм-аутом. При потере ответа запрашиваем
  `GET /payments?order_id=…`: если списание найдено, ставим `paid`.
  Если список пуст или проверка не удалась, оставляем `pending`.
  Отсутствие ответа не считается отказом банка.
- После ошибки повторяем обработку с паузой 1, 2, 4, затем 8 секунд.
  Количество попыток не ограничено.
- После трёх последовательных сетевых сбоев Payment общий circuit breaker
  приостанавливает запросы на 5 секунд. Затем разрешает один пробный запрос.
  Полученный HTTP-ответ возвращает обычный режим, сетевой сбой продлевает паузу.
  Уже начавшиеся запросы могут завершиться во время паузы.
  Ответ `500` не закрывает доступ к сервису для остальных заказов:
  неудавшаяся оплата повторяется с собственной паузой заказа.
- Резервирование и снятие резерва тоже можно безопасно повторять:
  Inventory обеспечивает это по `order_id`. Ошибка склада не отклоняет заказ.

Данные ожидающих заказов и шаг обработки хранятся в PostgreSQL.
После запуска задачи снова выбирают `pending`. Если процесс остановился
между внешним вызовом и записью результата, вызов повторится с тем же
идентификатором. Состояние circuit breaker при перезапуске сбрасывается.

Контракт Orders допускает нулевые цены, а Payment принимает только
положительную сумму. Поэтому бесплатный заказ после резервирования
становится `paid` без запроса на списание.

Ограничение ответа в 1 секунду обеспечивается отделением сетевых вызовов
от приёма заказа. Это предполагает работающую базу, как в сценариях задания 1.
Задание 2 (шина событий и бонусы) не реализовано.

## Запуск и проверка

Из корня репозитория:

```sh
make up
make scenarios TASK=1
```

Отдельные тесты оплаты и circuit breaker (после сборки образа):

```sh
docker compose run --rm --no-deps -v "$PWD/orders:/tests:ro" orders \
  python -m unittest discover -s /tests -v
```

Переменные окружения: `DATABASE_URL`, `PAYMENT_URL`, `INVENTORY_URL`,
`PORT` (по умолчанию `8080`).

Проверено на открытых параметрах стенда: S1–S5 — `PASS`, уровень
«полностью», стандартная пауза 30 секунд. Максимальный ответ на создание
заказа — около 0,02 секунды; в S4 — 23 обращения к Payment при лимите 30.
Девять отдельных тестов прошли. HTML-отчёт: `results/task_1.html`.
